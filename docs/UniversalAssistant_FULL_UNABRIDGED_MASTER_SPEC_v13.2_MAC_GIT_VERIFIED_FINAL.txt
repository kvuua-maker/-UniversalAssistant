IMPORTANT: - Treat this entire file as ONE indivisible specification. -
Do not summarize, compress, merge away, or weaken requirements. - Prefer
the deepest legitimate integration that materially improves the user
outcome; use a simpler verified path when it is equally effective or
when deeper integration is unavailable, disproportionate, or not
justified by evidence. - Continue beyond planning/scaffolding/code into
build and evidence-backed validation, while checkpointing and avoiding
repeated work or unnecessary limit consumption. - Continue through
build, tests, fixes, optimization, real-device test preparation,
TestFlight preparation, and App Store preparation. - Where current
Apple/provider rules differ from assumptions in this spec, verify
current official documentation and preserve the PRODUCT INTENT using the
deepest legitimate implementation. - Never claim an external integration
is complete if only a mock was tested. - Never claim a factual live
value unless it is actually verified.

1.  PRODUCT MISSION Build a real production-quality universal personal
    assistant for iPhone. It is not primarily a chatbot, AI wrapper,
    link collection, prototype, or mockup. It is an action-oriented
    assistant that turns a spoken or typed human need into the shortest
    legitimate real-world action.

2.  CORE PRODUCT PHILOSOPHY The defining experience is: SAY IT → IT GETS
    DONE → FORGET ABOUT IT. The user should not need to think which app,
    website, map, taxi service, retailer, calendar, ticket service, or
    provider to use.

3.  PRIMARY UX PRIORITIES Priority order: 1) safety/legal/platform truth
    and factual correctness; 2) user intent and minimum user effort; 3)
    responsive/no-stall behavior; 4) reliability; 5)
    privacy/security/data minimization; 6) speed/time-to-action; 7)
    feature breadth. Feature count never justifies an incorrect, unsafe,
    slow or unstable product.

4.  CODEX ROLE Act simultaneously as senior iOS/Swift/SwiftUI engineer,
    Apple-platform architect, backend architect, database engineer,
    API/integration engineer, natural-language command-engine engineer,
    location/navigation engineer, performance engineer, security/privacy
    engineer, UX engineer, QA engineer, DevOps engineer, and App Store
    release engineer.

5.  FULL LIFECYCLE RESPONSIBILITY Own the lifecycle: verify current
    platform capabilities → inspect environment → architecture →
    implementation → build → automated tests → fixes → retests →
    optimization → real-device test preparation → TestFlight preparation
    → App Store preparation.

6.  CONTINUE TO EVIDENCE, THEN STOP THE BLOCK Planning/scaffolding/code
    alone is not completion. Continue the current coherent block through
    proportionate build/test/evidence, then checkpoint and stop that
    block once acceptance is satisfied. Do not keep polishing or
    repeating work after the required evidence exists.

7.  AUTONOMOUS EXECUTION For ordinary engineering decisions, work
    autonomously. Do not ask the owner questions that can be resolved
    through official documentation, repository inspection, build output,
    tests, or engineering judgment.

8.  FAILURE LOOP Normal engineering failure is not a reason to stop.
    Required loop: FAILURE → DIAGNOSE → FIX → TEST → CONTINUE.

9.  ONLY REAL OWNER BLOCKERS Ask the owner only for genuinely
    unavailable external requirements such as credentials, paid account,
    CAPTCHA, 2FA, partner approval, commercial/legal agreement,
    Apple-account action, physical iPhone action, or an owner-only
    business decision.

10. ONE PROVIDER NEVER BLOCKS PROJECT If one external provider is
    blocked, document it, implement the deepest legitimate fallback,
    test that fallback, and continue the rest of the project.

11. GIT SOURCE OF TRUTH Use the designated Git repository as the project
    source of truth. Do not place secrets, personal data, production
    tokens, or credentials in Git.

12. CHECKPOINT AFTER EACH BLOCK After each meaningful completed block:
    build, run relevant tests, fix failures, update progress
    documentation, commit, push when authenticated, then continue.

20. NO FAKE COMPLETION Never mark the application or integration
    complete merely because code exists, a mock passes, or the UI looks
    correct.

21. NO FAKE LIVE DATA Never invent or falsely confirm price, stock,
    size/color availability, ticket availability, table availability,
    booking, purchase, taxi price, taxi ETA, vehicle availability,
    business open-now status, GPS location/accuracy, call completion,
    message delivery, or external-app integration.

22. MOCKS ARE NOT PRODUCTION PROOF Mocks may validate internal code
    paths but never count as proof that a production third-party
    integration works.

23. SOURCE METADATA For live-sensitive external facts retain source,
    retrieval time, freshness/expiration where applicable, and
    verification status.

24. DO DON’T NARRATE Absolute UX rule: if a command is clear and
    executable, perform it. Do not narrate obvious processing or action.

25. AVOID UNNECESSARY PHRASES Avoid phrases such as ‘I found it’, ‘I am
    opening it’, ‘I will do that now’, ‘I am searching’, ‘I understood’,
    unless the words themselves convey necessary information.

26. SILENT OPEN EXAMPLE ‘Покажи нову колекцію Baldinini’ should open the

28. SILENT APP OPEN EXAMPLE ‘Відкрий Укрзалізницю’ should immediately

29. SILENT CALENDAR EXAMPLE ‘Запиши стоматолога завтра о 10’ should

30. SHORT VISUAL CONFIRMATIONS Use compact visual confirmations such as
    ✓ Готово, ✓ Записано, ✓ Скасовано. They should disappear
    automatically after an appropriate short period.

31. WHEN SPEECH IS JUSTIFIED Use speech only for useful factual results,
    genuine ambiguity, warning, inability to verify, necessary user
    decision, or mandatory system/safety confirmation.

32. ZERO FRICTION Never ask what the application already knows from
    explicit user configuration or previously confirmed structured
    preferences.

33. REUSE HOME WORK Reuse explicit Home/Work locations rather than
    repeatedly asking for them.

34. REUSE CONTACT ALIASES Reuse confirmed aliases such as

35. REUSE DEFAULT MAP Reuse the configured default navigation app unless

36. REUSE TAXI RULE Reuse explicit taxi preferences such as ‘cheapest if
    wait ≤7 min’ without asking again.

37. ONLY REAL AMBIGUITY Ask one short clarification only when there is
    real ambiguity, risk of a materially wrong action, or an iOS/system
    requirement.

38. NEVER FREEZE No provider, API, backend, database operation, network
    request, or connector may indefinitely block the UI.

39. ASYNC EXTERNAL WORK All external work must be asynchronous and kept
    off the main UI thread where appropriate.

40. TIMEOUT EVERY EXTERNAL CALL Every external operation that can stall
    must have a timeout.

41. CANCELLATION Support cancellation of obsolete or superseded work
    where safe.

42. FAILURE ISOLATION A failure in one connector must not crash or
    disable unrelated modules.

43. NO PERMANENT SPINNER Never leave the user on a permanent loading
    indicator. Time out, fall back, or return a truthful limited result.

44. LAZY LOADING Load heavy feature modules only when needed.

45. PARALLEL PROVIDER REQUESTS Run provider calls in parallel when that
    meaningfully reduces time-to-result and does not create waste/abuse.

46. REQUEST DEDUPLICATION Deduplicate equivalent simultaneous requests
    and reuse safe in-flight/cached results where appropriate.

47. BOUNDED CACHES Use bounded caches with explicit freshness rules. Do
    not allow unbounded memory/storage growth.

48. MINIMAL MAIN THREAD Keep heavy parsing, networking, database and
    provider work off the main thread.

49. ON DEMAND INITIALIZATION Do not initialize all providers, business
    modules, ticket engines, grocery engines, etc. at app launch.

50. COFFEE MODULE EXAMPLE For ‘Хочу кави’, activate only Voice → Command
    → Location → Places → Route; unrelated modules remain inactive.

51. RESOURCE CONTROL Continuously consider RAM, CPU, battery, network
    usage, storage, and duration of high-accuracy GPS.

52. TIME TO ACTION METRIC Measure Time-to-Action from the end of the
    user’s command to a useful action/result.

53. LOCAL COMMANDS FEEL IMMEDIATE Simple local commands such as
    calendar/reminder/known contact actions should feel effectively
    immediate.

54. FIRST RELIABLE RESULT For network searches, do not wait for a slow
    secondary provider once a sufficiently reliable useful result is
    available, unless comparison accuracy specifically requires waiting.

55. BAD NETWORK SUPPORT Explicitly support slow internet, packet loss,
    offline mode, timeouts, provider outages, backend outages, and
    interrupted requests.

56. BACKGROUND FOREGROUND Correctly handle moving between
    foreground/background without stale UI state, duplicate actions, or
    frozen workflows.

57. BACKEND DOWN LOCAL CONTINUES If our backend is unavailable,
    local/system functions that can legitimately work should continue:
    contacts, calendar, reminders, internal notes, some device actions,
    safe non-live cached data.

58. NEW COMMAND CANCELS OLD If the user changes intent, cancel obsolete
    work where safe. Example: restaurant search interrupted by ‘ні,
    знайди аптеку’.

59. MULTIPLE PROVIDER FAILURE Test and recover when several providers
    fail simultaneously.

60. LOW MEMORY RESILIENCE Design and test graceful behavior under memory

1100. PROJECT STATUS DASHBOARD Maintain PROJECT_STATUS.md as the single

1101. STATUS MUST BE CURRENT Update PROJECT_STATUS.md at every

1102. MACHINE READABLE HEARTBEAT Maintain a machine-readable
      PROGRESS_HEARTBEAT.json or equivalent containing current
      block/action, status, last measurable progress timestamp, current
      attempt/path identifier, last commit and blocker state.

1103. HEARTBEAT IS PROGRESS SIGNAL NOT BUSY SIGNAL Do not update the
      heartbeat merely to claim activity. A progress timestamp changes
      only for measurable progress or a meaningful diagnostic
      conclusion.

1104. MEASURABLE PROGRESS DEFINITION Measurable progress includes a
      newly passing build/test, reduced/changed failure caused by a
      material fix, verified root cause, verified provider/platform
      limitation, successful real integration action, completed working
      fallback, or another objectively changed project state.

1105. NO FAKE PROGRESS Re-running the same command, rewriting equivalent
      code, re-reading the same output, or reporting ‘still working’ is
      not measurable progress.

1106. ATTEMPT LEDGER Maintain ATTEMPT_LEDGER.json or equivalent
      structured ledger for failed technical paths, including problem,
      method/path signature, material inputs/configuration, error
      signature, evidence, diagnosis, documentation checked, conclusion
      and next hypothesis.

1107. FAILED PATH MEMORY Once a deterministic method/path has failed and
      its relevant conditions are unchanged, record it as FAILED_PATH so
      Codex does not unknowingly repeat it later in the same or future
      session.

1108. DETERMINISTIC FAILURE — AVOID UNCHANGED RETRIES After a
      deterministic failure, do not keep repeating the same method under
      unchanged material conditions. A single bounded verification retry
      is acceptable when diagnostic uncertainty, transient environment
      state, or test flakiness reasonably justifies it; otherwise
      require new evidence or a material change before retrying.

1109. SAME FAILURE SAME METHOD STOP SAME deterministic failure + SAME
      method + NO material change = DO NOT RUN AGAIN.

1110. ANALYZE AFTER FIRST FAILURE Immediately after the first
      deterministic failure, inspect the exact error/evidence, relevant
      code/configuration/state and current authoritative documentation
      before choosing the next action.

1111. MATERIAL CHANGE REQUIRED A subsequent execution is permitted only
      after a material change that has a reasoned connection to the
      diagnosed failure.

1112. MATERIAL CHANGE EXAMPLES Material change may include a substantive
      code fix, different supported API/endpoint, corrected OAuth
      scope/authorization, configuration change, dependency/version
      change, algorithm change, architecture/path change, required
      entitlement becoming available, or another verified change capable
      of affecting the failure.

1113. COSMETIC CHANGE IS NOT MATERIAL Renaming variables, reformatting
      code, rerunning an unchanged build/request, reopening the same
      page, or changing irrelevant parameters does not qualify as a
      material change.

1114. RETRY JUSTIFICATION BEFORE EXECUTION Before any post-failure
      re-execution, record: WHAT materially changed; WHY that change can
      resolve the prior failure; WHAT observable result will confirm or
      falsify the new hypothesis.

1115. NO JUSTIFICATION NO EXECUTION If Codex cannot state a material
      change and a causal reason the result may differ, it MUST NOT
      execute the same path again.

1116. NEW HYPOTHESIS REQUIRED After a deterministic failed path, the
      next attempt must test a genuinely new hypothesis rather than
      hoping the same operation succeeds.

1117. ALTERNATIVE APPROACH MUST BE ACTUALLY DIFFERENT Codex may call a
      path ‘alternative’ only if implementation, API, authorization,
      configuration, algorithm, dependency, architecture, or another
      material assumption actually changed.

1118. TRANSIENT FAILURE EXCEPTION A bounded retry is permitted only for
      evidence-based transient failures such as network timeout,
      temporary connection loss, HTTP 429/5xx or explicitly temporary
      provider state where conditions can change without code changes.

1119. TRANSIENT RETRY MUST BE BOUNDED Transient retries must use
      appropriate backoff/jitter/provider guidance and a strict finite
      limit; never retry indefinitely.

1120. DETERMINISTIC ERRORS ARE NOT TRANSIENT Invalid credentials,
      missing entitlement, unsupported API, compiler/type error, invalid
      endpoint, denied permanent permission, documented provider
      restriction and equivalent deterministic failures must not be
      retried unchanged.

1121. DOCUMENTATION PROVES IMPOSSIBLE PATH If current authoritative
      documentation proves a path unsupported/impossible, close that
      path immediately, record the evidence and investigate the next
      legitimate integration mechanism. Never ‘try it again just in
      case’.

1122. EXTERNAL BLOCKER HANDLING If diagnosis proves an external blocker
      such as missing credential, 2FA, CAPTCHA, Apple entitlement,
      partner approval, paid account, provider restriction or required
      physical-device action, record the precise blocker and stop
      spending Codex effort on unchanged attempts.

1123. BLOCKER DOES NOT STOP PROJECT After an external blocker: implement
      everything possible up to the boundary → test what can be tested →
      commit → mark precise status → immediately continue the next
      independent block.

1124. INTERNAL SOLVABLE PROBLEM MUST BE SOLVED Anti-stall rules are not
      permission to abandon a technically solvable internal problem. If
      no external blocker exists and the requirement is feasible, Codex
      MUST seek a materially different solution until it is solved.

1125. ANTI STALL REVIEW If there is no measurable progress for 30
      minutes on a non-long-running operation, Codex must stop the
      current approach, review the ledger/evidence/documentation and
      choose a materially different path or prove an external blocker.

1126. LONG RUNNING OPERATION EXCEPTION A legitimate long
      build/test/download/migration may exceed the review interval if it
      is demonstrably still progressing. Do not kill healthy work merely
      because wall-clock time passed.

1127. NO REPEATED DOCUMENTATION LOOP Do not repeatedly search/read the

      conclusions and use them.

1128. NO REPEATED BUILD LOOP Do not rerun an unchanged deterministic

1129. NO REPEATED API LOOP Do not resend the same deterministic failing

      and relevant provider state.

1130. NO REPEATED INSTALL CONFIG LOOP Do not repeatedly

1131. LIMIT CONSERVATION RULE Treat Codex usage/time as a finite

      process defect to avoid because it wastes project time and usage

      App Store merely because a milestone or Owner Test Build passed.
      Public release requires explicit owner authorization after
      release-readiness information is presented.

1190. CONTINUE BEYOND FIRST TESTABLE BUILD A successful first Owner Test
      Build is not a stop condition. Continue implementing subsequent
      specification blocks unless the owner explicitly pauses the
      project.

1191. FINAL OWNER TEST AUDIT Before release readiness, reconcile
      OWNER_TEST_QUEUE, REAL_DEVICE_TEST_MATRIX and INTEGRATION_STATUS
      so every device-required capability is PASS, legitimately blocked,
      or explicitly deferred by owner decision.

1192. PRE IMPLEMENTATION FEASIBILITY GATE Before substantial
      implementation of a materially uncertain system/third-party
      integration, Codex should establish enough feasibility evidence to
      avoid speculative large builds. For obvious, low-risk,
      well-documented platform work, keep the proof lightweight and
      proportional rather than creating ceremony for its own sake.

1193. FIRST PROVE THEN BUILD Engineering rule: obtain proportionate
      evidence that the required capability is feasible through the
      selected legitimate path before investing in substantial
      implementation.

1194. NO FULL IMPLEMENTATION BEFORE PROOF Avoid building a large/full
      integration around an unproven external/system capability. Use a
      small proof or official evidence first when uncertainty is
      material.

1195. FEASIBILITY GATE PURPOSE The feasibility gate exists to prevent
      wasted Codex limits, implementation churn, abandoned code,
      speculative rewrites, and late discovery that an
      API/provider/platform path cannot satisfy the requirement.

1196. FEASIBILITY OFFICIAL SOURCES FIRST For platform/provider
      feasibility, inspect current authoritative official documentation
      first: Apple documentation, provider API/SDK/OAuth/App
      Intent/Shortcut/deep-link documentation, official
      terms/entitlement/partner requirements, and actual current
      supported capabilities.

1197. FEASIBILITY EXACT REQUIRED CAPABILITY Do not merely prove that an
      API/provider exists. Prove that the exact capability required by
      the product is supported to the required depth.

1198. FEASIBILITY REQUIREMENTS LIST Before testing a path, list the
      exact required actions for that integration, such as READ, SEARCH,
      CREATE, UPDATE, DELETE, BOOK, QUOTE, STOCK, ETA, SEND,
      OPEN_EXACT_CONTEXT, AUTHORIZATION, BACKGROUND_WATCH or other
      relevant capabilities.

1199. FEASIBILITY ACCESS REQUIREMENTS Before implementation, identify
      required credentials, OAuth scopes, entitlements, Apple
      capabilities, account type, provider approval, commercial
      agreement, region restrictions, rate limits and device
      requirements.

1200. FEASIBILITY TERMS LEGITIMACY Verify that the proposed integration
      path is legitimate under current platform/provider rules. A
      technically possible but prohibited/private/scraping/bypass path
      fails the gate.

1201. FEASIBILITY MINIMAL PROOF Where technically possible with
      available access, perform the smallest real proof-of-capability
      that demonstrates the selected path can execute the required core
      action.

1202. MINIMAL PROOF MUST BE REAL WHEN POSSIBLE If credentials/test
      account/device are available, the proof-of-capability must use the
      real provider/system. A mock cannot prove external feasibility.

1203. MINIMAL PROOF MUST BE SMALL Do not build the full module to prove
      feasibility. Use the smallest controlled experiment necessary to
      answer whether the path can satisfy the requirement.

1204. FEASIBILITY EXAMPLE GMAIL For Gmail, verify official OAuth/API
      availability, required scopes and account restrictions, then
      perform a minimal real authorized query before building the full
      Gmail integration.

1205. FEASIBILITY EXAMPLE CALENDAR For Calendar, verify current
      EventKit/public Apple capability for the exact required
      create/read/update/delete behavior before building the full
      Calendar command layer.

1206. FEASIBILITY EXAMPLE TAXI For a taxi provider, verify whether
      current public/partner mechanisms expose actual quote/ETA/order
      capabilities before implementing a comparison/order engine for
      that provider.

1207. FEASIBILITY EXAMPLE RETAIL For a retailer, verify whether official
      current sources expose the exact price/stock/catalog capability
      needed before writing a full retailer adapter.

1208. FEASIBILITY RESULT STATES Every feasibility gate must end in
      exactly one clear state: PASS_SELECTED_PATH, EXTERNAL_BLOCKED,
      UNSUPPORTED, or NEEDS_OWNER_ACCESS_FOR_PROOF.

1209. PASS_SELECTED_PATH Use PASS_SELECTED_PATH only when current
      evidence proves the selected legitimate path can satisfy the
      required capability to the intended depth.

1210. EXTERNAL_BLOCKED FEASIBILITY Use EXTERNAL_BLOCKED when the
      capability appears supported but a specific external requirement
      such as credential, entitlement, partner approval, paid account,
      2FA or physical-device action prevents proof/implementation.

1211. UNSUPPORTED FEASIBILITY Use UNSUPPORTED only when current
      legitimate public capabilities have been exhaustively checked and
      the required capability is not available.

1212. NEEDS OWNER ACCESS FOR PROOF Use NEEDS_OWNER_ACCESS_FOR_PROOF only
      when feasibility cannot be completed without a specific owner
      action; record exactly what is needed and continue all independent
      work.

1213. NO IMPLEMENTATION ON FAILED GATE If feasibility evidence shows the
      capability is unsupported, do not spend substantial implementation
      budget constructing an unavailable integration. Use the deepest
      legitimate useful fallback and continue.

1214. BLOCKED GATE LIMIT DISCIPLINE If feasibility is
      EXTERNAL_BLOCKED/NEEDS_OWNER_ACCESS_FOR_PROOF, Codex must
      implement only components that remain valid regardless of the
      blocked proof, then stop that path and continue independent work.

1215. IMPLEMENTATION BUDGET UNLOCK Substantial implementation work for a
      path is unlocked only after PASS_SELECTED_PATH or after an
      explicitly justified boundary implementation that cannot be
      invalidated by the unresolved external proof.

1216. ONE TASK ONE ACTIVE PATH For each concrete task/integration, only
      ONE implementation path may be ACTIVE at a time.

1217. NO PARALLEL TECHNOLOGY EXPERIMENTS Do not build multiple competing
      implementations/frameworks/architectures for the same task in
      parallel merely to compare them.

1218. FINISH BEFORE SWITCHING After a path passes feasibility and
      becomes ACTIVE, Codex MUST finish it to SUCCESS,
      PROVEN_PATH_FAILURE, or EXTERNAL_BLOCKED before starting an
      alternative implementation.

1219. INCOMPLETE IS NOT FAILED An implementation being unfinished,
      difficult, time-consuming, or requiring debugging is NOT evidence
      that the selected path is wrong.

1220. NO MID TASK TECHNOLOGY SWITCH BY PREFERENCE After feasibility
      PASS, avoid switching technology/framework/API/architecture merely
      for novelty or preference. Switch when new evidence shows a
      material benefit, a defect, a platform change, or a simpler path
      with equal/better outcomes.

1221. NO SPECULATIVE REWRITE Do not rewrite a working or still-valid
      implementation speculatively. A rewrite requires objective
      evidence that the current path cannot meet a mandatory requirement
      or has a measured critical deficiency.

1222. NO PREMATURE OPTIMIZATION Do not replace or redesign a correct
      path for speculative performance optimization before it works
      end-to-end and measured evidence shows a relevant performance
      problem.

1223. WORKING CORRECT TESTED THEN OPTIMIZE Required order: WORKING →
      CORRECT → TESTED → MEASURED → OPTIMIZE ONLY IF NEEDED.

1224. PATH CHANGE ONLY ON NEW EVIDENCE After feasibility PASS, a path
      change is permitted only when NEW objective evidence appears that
      was not reasonably available/known at the gate and proves the
      current path cannot meet a mandatory requirement.

1225. PATH CHANGE EVIDENCE REQUIREMENT Before any path change, record
      the new evidence, the exact mandatory requirement the current path
      cannot satisfy, why the limitation cannot be fixed within the
      current path, and why the proposed replacement specifically
      resolves it.

1226. NO PATH CHANGE WITHOUT PROOF If Codex cannot prove the current
      selected path is incapable of satisfying a mandatory requirement,
      it MUST continue and finish the current path.

1227. PATH CHANGE IS EXCEPTION Changing implementation technology after
      feasibility PASS is an exceptional recovery action, not a normal
      development style.

1228. NO REOPENING CLOSED ARCHITECTURE DECISIONS Do not repeatedly
      reconsider already-proven architecture/technology choices unless
      new objective evidence invalidates the original decision.

1229. FEASIBILITY DECISION RECORD Record each passed feasibility
      decision in FEASIBILITY_REGISTRY.md with task, required
      capabilities, selected path, official evidence checked, proof
      result, access requirements, decision, and date/build/context.

1230. FEASIBILITY REGISTRY IS SOURCE OF PATH MEMORY Before starting any
      integration/task, Codex MUST consult FEASIBILITY_REGISTRY.md so it
      does not rediscover, re-evaluate, or switch away from
      already-proven paths without new evidence.

1231. FAILED FEASIBILITY PATH MEMORY Record failed/unsupported
      feasibility paths so Codex does not later spend limits
      investigating the same rejected mechanism without new evidence.

1232. DISCOVERY MUST TERMINATE ON EVIDENCE Once authoritative evidence
      conclusively proves a legitimate path unsupported, blocked by
      unavailable entitlement/partner status, or otherwise unable to
      satisfy the required capability, stop investigating that exact
      path.

1233. NO ENDLESS PROVIDER RESEARCH Do not search dozens of equivalent
      unofficial methods after current official evidence has
      conclusively established the platform/provider boundary.

1234. DEEPER PATH CHECK IS BOUNDED BY OFFICIAL EVIDENCE The requirement
      to seek the deepest legitimate integration does not authorize
      endless speculative exploration. Investigate each relevant
      official integration avenue once with a specific capability
      question and record the conclusion.

1235. NO RESEARCH WITHOUT QUESTION Documentation/API investigation
      should answer a concrete unresolved question. Avoid broad browsing
      that has no decision or evidence target.

1236. NO RESEARCH LOOP Do not repeatedly read the same documentation,
      search the same provider capability, or reopen the same
      feasibility question unless a new requirement, version,
      documentation change, credential state or concrete contradictory
      evidence appears.

1237. LIMIT FIRST ENGINEERING Treat Codex limit consumption as an
      engineering constraint. Before expensive implementation, choose
      the cheapest reliable method to eliminate feasibility uncertainty.

1238. CHEAP PROOF BEFORE EXPENSIVE BUILD A short documentation check or
      minimal API proof must be preferred over hours of code when either
      can determine viability.

1239. NO THROWAWAY LARGE IMPLEMENTATION Producing substantial code that
      is likely to be discarded because feasibility was not checked
      first is a process failure.

1240. WASTED REWORK MUST BE PREVENTED NOT JUST RECORDED The goal is not
      merely to document wasted work; Codex MUST actively prevent
      avoidable rework through feasibility gating, single-path
      discipline and evidence-based path locking.

1241. ACTIVE TASK LOCK While a task is active, keep focus on its
      coherent block until completion/blocker state. Avoid unrelated
      technology experiments unless they directly unblock or materially
      improve the active task.

1242. NO TASK HOPPING WITHIN BLOCK Do not jump from one unresolved
      implementation task to another unrelated implementation task
      merely because the first became difficult. Resolve it, prove a
      blocker, or finish the coherent block according to dependency
      rules.

1243. DEPENDENCY EXCEPTION FOR TASK HOPPING Switching to an independent
      task is allowed only when the current task is externally blocked,
      requires owner/device input, is waiting on a legitimate
      long-running external process, or continuing it would be
      objectively impossible until another prerequisite is completed.

1244. TASK COMPLETION CRITERIA BEFORE START Before implementation
      begins, define the concrete completion criteria for the current
      task so Codex cannot redefine success midway.

1245. DO NOT EXPAND TASK MID IMPLEMENTATION Do not silently enlarge the
      scope of the active task with optional improvements/features.
      Finish the agreed mandatory scope first.

1246. OPTIONAL IMPROVEMENTS BACKLOG Potential improvements discovered
      during implementation must be placed into a backlog unless they
      are required to satisfy the current mandatory specification.

1247. NO REFACTOR DETOUR Do not start unrelated refactoring while
      implementing a feature unless the refactor is strictly necessary
      to complete that feature safely/correctly.

1248. NO TOOL TECHNOLOGY SHOPPING Do not repeatedly evaluate alternative
      libraries/frameworks/tools after a viable selected path has passed
      feasibility.

1249. PREFER EXISTING PROVEN STACK When the existing project stack
      already satisfies the requirement, use it rather than introducing
      a new technology without a demonstrated mandatory need.

1250. NEW DEPENDENCY GATE Adding a new significant dependency/framework
      requires proof that the existing selected stack cannot reasonably
      satisfy the mandatory requirement or that the dependency provides
      a clearly measured material benefit.

1251. OWNER CLARITY CONTRACT The owner must NEVER be required to infer
      project state from technical files, logs, Git history, matrices,
      or Codex internal reasoning.

1252. ONE OWNER STATUS FILE Maintain OWNER_STATUS.md as the single
      simple owner-facing status surface. All technical status files
      remain internal engineering records.

1253. OWNER STATUS TEN SECOND RULE At any time, the owner must be able
      to understand the current project state from OWNER_STATUS.md
      within approximately 10 seconds.

1254. OWNER STATUS REQUIRED SECTIONS OWNER_STATUS.md must contain only:
      DONE AND CODEX-VERIFIED; CURRENTLY WORKING ON; NEEDS OWNER IPHONE
      TEST; BLOCKED AND WHY; OWNER ACTION NEEDED NOW; NEXT.

1255. OWNER STATUS PLAIN LANGUAGE OWNER_STATUS.md must use plain
      non-technical language. Do not expose API names, error codes,
      internal architecture, attempt ledgers or engineering jargon
      unless the owner explicitly asks.

1256. OWNER ACTION BINARY OWNER_STATUS.md must state clearly either
      ‘ТОБІ ЗАРАЗ НІЧОГО РОБИТИ НЕ ТРЕБА’ or the exact single/simple
      owner action currently needed.

1257. NO OWNER MULTI FILE NAVIGATION If the owner must inspect multiple
      files to understand what is ready, blocked, being tested, or what
      to do next, the status system has failed.

1258. OWNER STATUS TEST INSTRUCTIONS When owner testing is needed,
      OWNER_STATUS.md should show only the short human test list: exact
      phrase/action and expected visible outcome, linked internally to
      detailed Test IDs.

1259. OWNER STATUS NO QUEUE DUMP Do not dump hundreds of queued tests
      into OWNER_STATUS.md. Present only the current recommended owner
      test batch and summarize deferred tests.

1260. OWNER STATUS BLOCKER SIMPLICITY A blocker must be explained in one
      short sentence describing what is missing and whether the owner
      needs to act.

1261. OWNER STATUS CURRENT WORK Show one current primary block/task, not
      a confusing list of many simultaneous active tasks.

1262. OWNER STATUS PATH STABILITY For the current task, show whether the
      selected technical path is STABLE or whether a proven external
      blocker/new evidence forced a change; do not burden the owner with
      implementation details.

1263. OWNER STATUS LIMIT PROTECTION If Codex detects avoidable repeated
      work, architecture churn, or path switching, OWNER_STATUS.md must
      flag PROCESS ISSUE rather than hiding it.

1264. OWNER STATUS AUTOMATIC UPDATE Update OWNER_STATUS.md whenever a
      coherent block completes, owner action becomes
      necessary/unnecessary, a device test batch becomes ready, a
      blocker is proven, or the active task changes.

1265. OWNER STATUS SURVIVES SESSION Commit/push OWNER_STATUS.md with
      normal progress checkpoints so the owner-facing state survives
      Codex/Mac/session interruption.

1266. OWNER STATUS REMOTE VISIBILITY Ensure OWNER_STATUS.md is available
      through the project’s persistent remote/source-of-truth workflow
      when authenticated, not only as an uncommitted local Mac file.

1267. NO FALSE OWNER URGENCY Do not surface an owner action merely
      because a technical task is inconvenient for Codex. Owner action
      is requested only when it is genuinely unavailable to Codex.

1268. FINAL FEASIBILITY AUDIT Before project completion, verify that
      every substantial external/system integration had a feasibility
      decision before expensive implementation or document any exception
      and why it was unavoidable.

1269. FINAL PATH DISCIPLINE AUDIT Verify no task changed implementation
      technology after feasibility PASS without documented new objective
      evidence proving the original path incapable of meeting a
      mandatory requirement.

1270. FINAL LIMIT WASTE AUDIT Audit for repeated research, abandoned
      large implementations, parallel competing implementations,
      unnecessary dependency/framework switches and premature rewrites.
      Any avoidable occurrence is a PROCESS FAILURE.

1271. FINAL OWNER CLARITY AUDIT Verify the owner can determine what is
      done, current work, blockers, current test batch, and required
      action from OWNER_STATUS.md alone without reading technical
      artifacts.

1272. FEASIBILITY PASS PER CAPABILITY Feasibility is evaluated per exact
      required capability, not merely per provider, app, framework or
      integration name.

1273. NO PROVIDER LEVEL BLANKET PASS Codex MUST NOT mark an entire
      provider/integration PASS merely because one API call or one
      subset of actions works.

1274. CAPABILITY MATRIX BEFORE PASS For each integration explicitly
      classify every required capability such as SEARCH, READ, CREATE,
      UPDATE, DELETE, SEND, BOOK, QUOTE, ETA, STOCK, OPEN_EXACT_CONTEXT,
      BACKGROUND_WATCH and AUTHORIZATION before implementation.

1275. MIXED CAPABILITY STATES A single provider may have different
      states per capability, e.g. SEARCH=PASS, READ=PASS, SEND=BLOCKED,
      DELETE=UNSUPPORTED. Preserve these distinctions.

1276. IMPLEMENT ONLY PROVEN CAPABILITY DEPTH Implementation scope
      follows the proven capability matrix; do not infer unsupported
      deeper actions from a shallower successful proof.

1277. FEASIBILITY CLOSES AFTER PASS Once an exact capability/path
      receives PASS_SELECTED_PATH, its feasibility investigation is
      CLOSED and Codex proceeds to implementation.

1278. NO FEASIBILITY REOPEN WITHOUT TRIGGER A closed feasibility
      decision may not be reopened for curiosity, second-guessing,
      technology shopping or speculative improvement.

1279. VALID FEASIBILITY REOPEN TRIGGERS Reopen only for a new mandatory
      requirement, relevant API/SDK/platform version change, new
      authoritative documentation, concrete runtime contradiction,
      changed credential/entitlement state, or other new objective
      evidence capable of invalidating the prior decision.

1280. REOPEN MUST NAME NEW EVIDENCE Before reopening a closed
      feasibility decision, record the new evidence/trigger and why it
      may change the prior conclusion. Avoid reopening without a
      concrete reason.

1281. ATOMIC ACTIVE TASK The ACTIVE TASK must be small and concrete
      enough to reach a clear exit state without becoming a broad
      umbrella for unrelated implementations.

1282. NO VAGUE ACTIVE TASK Do not use vague active tasks such as
      ‘Implement Gmail’, ‘Do integrations’, ‘Build backend’, or ‘Fix
      app’. Break them into coherent finishable tasks such as ‘Gmail
      Search Messages’, ‘Calendar Create Event’, or ‘Taxi Provider Quote
      Capability’.

1283. TASK BOUNDARY BEFORE START Before starting an ACTIVE TASK define
      its exact input, required behavior/output, dependencies,
      acceptance tests and exit criteria.

1284. ONE ATOMIC TASK ONE PATH Each atomic ACTIVE TASK has exactly one
      selected implementation path after feasibility PASS.

1285. NO HIDDEN SUBTASK HOPPING Do not use a broad parent task to
      justify hopping among unresolved child tasks. Each child requiring
      independent implementation receives its own atomic task/exit
      state.

1286. RESULT BEFORE NEXT TASK Codex MUST NOT begin the next
      implementation task until the current ACTIVE TASK has reached an
      explicit allowed exit state.

1287. ALLOWED TASK EXIT STATES The only normal ACTIVE TASK exit states
      are SUCCESS, EXTERNAL_BLOCKED, UNSUPPORTED, DEVICE_TEST_REQUIRED,
      or DEPENDENCY_WAIT.

1288. SUCCESS EXIT SUCCESS requires implementation complete to defined
      scope, successful build and all technically available relevant
      Codex-side tests passed.

1289. EXTERNAL BLOCKED EXIT EXTERNAL_BLOCKED requires specific evidence
      of an external
      credential/account/approval/entitlement/provider/human blocker and
      completion of all safe work possible before that boundary.

1290. UNSUPPORTED EXIT UNSUPPORTED requires authoritative evidence that
      the exact capability cannot be legitimately implemented after the
      bounded integration-depth check.

1291. DEVICE TEST REQUIRED EXIT DEVICE_TEST_REQUIRED is allowed only
      after Codex completed/tested everything possible without the
      physical iPhone and queued an exact owner test.

1292. DEPENDENCY WAIT EXIT DEPENDENCY_WAIT is allowed only for a
      concrete prerequisite/legitimate long-running dependency; continue
      independent work where available.

1293. NO ABANDONED IN PROGRESS TASK An ACTIVE TASK may never be silently
      left unresolved IN_PROGRESS while Codex starts unrelated
      implementation work.

1294. COMPLETED VERIFIED COMMITTED FROZEN BASELINE A task/block that is
      completed, Codex-verified and committed becomes a FROZEN BASELINE.

1295. NO REOPEN FROZEN BASELINE BY PREFERENCE Do not rewrite, replace,
      refactor or re-architect a FROZEN BASELINE merely because another
      implementation appears cleaner, newer, more elegant or preferable.

1296. VALID FROZEN BASELINE CHANGE TRIGGERS A FROZEN BASELINE may change
      only for a demonstrated regression/bug, new mandatory requirement
      genuinely requiring change, security/privacy/correctness need,
      compatibility break, or new objective evidence proving it cannot
      satisfy the specification.

1297. MINIMAL CHANGE TO FROZEN BASELINE When a frozen baseline must
      change, make the smallest safe change necessary and preserve
      already passing behavior/tests.

1298. REGRESSION PROTECTION FOR FROZEN BASELINE Before modifying a
      frozen baseline identify affected passing tests; after
      modification rerun them and record regression status.

1299. NO CASCADING REWRITE WITHOUT PROOF A new feature must not trigger
      broad rewrites of completed modules unless a concrete dependency
      proves them necessary.

1300. FIXED INTEGRATION DEPTH ORDER For every important integration
      evaluate legitimate depth in fixed order where applicable:
      official direct API → official SDK → OAuth/partner API → App
      Intent → official Shortcut → Universal Link/deep link → legitimate
      structured feed/data → exact official web context → phone →
      navigation/opening/instruction.

1301. CHECK EACH RELEVANT DEPTH ONCE Each relevant integration-depth
      level is investigated once for a specific required capability and
      its conclusion recorded.

1302. SKIP INAPPLICABLE DEPTH WITH EVIDENCE A depth level may be skipped
      only when authoritative evidence shows it is inapplicable to that
      provider/capability.

1303. DEEPEST AVAILABLE PATH LOCK Once higher levels are proven
      unavailable/blocked and the deepest currently available legitimate
      level is proven, select and lock that path and stop discovery for
      that capability.

1304. NO RETURN TO HIGHER DEPTH WITHOUT NEW EVIDENCE Do not return to a
      closed higher integration level unless a valid feasibility-reopen
      trigger occurs.

1305. NO BLOG GITHUB LOOP AFTER OFFICIAL BOUNDARY Once official
      authoritative evidence establishes the capability boundary, do not
      continue searching blogs, forums, GitHub projects or unofficial
      workarounds hoping to bypass it.

1306. OFFICIAL CAPABILITY CHANGE RECHECK A relevant later official
      provider/platform capability change is valid new evidence and may
      reopen affected feasibility.

1307. OWNER STATUS THREE VERIFICATION LEVELS OWNER_STATUS.md must
      clearly distinguish: ГОТОВО — CODEX ПЕРЕВІРИВ; ГОТОВО — ПОТРІБНА
      ТВОЯ ПЕРЕВІРКА НА IPHONE; ПОВНІСТЮ ПЕРЕВІРЕНО.

1308. CODEX VERIFIED MEANING ГОТОВО — CODEX ПЕРЕВІРИВ means
      implementation is complete to current scope and all tests Codex
      can legitimately execute without owner physical-device action
      passed; it does NOT imply physical-iPhone verification.

1309. OWNER IPHONE TEST MEANING ГОТОВО — ПОТРІБНА ТВОЯ ПЕРЕВІРКА НА
      IPHONE means Codex-side verification is complete and only the
      explicitly listed physical-iPhone observation/action remains.

1310. FULLY VERIFIED MEANING ПОВНІСТЮ ПЕРЕВІРЕНО may be shown only after

1311. NO AMBIGUOUS DONE WORD Do not show bare DONE/ГОТОВО to the owner
      when device verification remains. Always show the correct
      verification level.

1312. OWNER TEST STATUS EXPANSION Detailed owner test records support
      NOT_TESTED, PASS, FAIL, RETEST_REQUIRED, BLOCKED_DELIVERY,
      BLOCKED_PERMISSION, EXPIRED_BUILD and SUPERSEDED where applicable.

1313. BLOCKED DELIVERY IS NOT TEST FAILURE If the build cannot currently

1314. BLOCKED PERMISSION IS DISTINCT If testing cannot proceed because

1315. EXPIRED BUILD IS DISTINCT An expired signing/provisioning/test

1316. SUPERSEDED TEST MANAGEMENT When a newer Owner Test Build makes an

      to the new build and mark obsolete old test instances SUPERSEDED.

1317. NO STALE BUILD TEST PILE Do not accumulate confusing queues tied
      to obsolete builds. OWNER_TEST_QUEUE identifies one current

1318. RETEST REQUIRED STATE After a material fix to a failed device
      test, mark RETEST_REQUIRED tied to the new build and original Test

1319. OWNER STATUS ONLY CURRENT TEST BATCH OWNER_STATUS.md shows only

      obsolete/superseded/deferred history remains internal.

1320. DEVICE TESTS THROUGHOUT DEVELOPMENT Physical-iPhone tests may

1321. M11 IS FINAL RECONCILIATION NOT FIRST DEVICE TEST M11 REAL DEVICE

1322. EARLY DEVICE TEST WHEN ARCHITECTURALLY IMPORTANT If early

1324. EARLY DEVICE DELIVERY PREFLIGHT During M0 perform a lightweight

1328. NO ARBITRARY OWNER BUILD COUNT Do not use an arbitrary number of

1329. UNIQUE FAILURE DIAGNOSIS RULE Diagnosis applies per UNIQUE FAILURE

1330. NEW FAILURE NEW DIAGNOSIS After a material fix, a genuinely

1331. DOCUMENTATION ONLY WHEN RELEVANT Do not automatically spend limits

1332. WHEN DOCUMENTATION IS REQUIRED Consult current authoritative

1334. ANTI STALL NEW EVIDENCE COUNTS AS PROGRESS For anti-stall timing,
      measurable progress includes genuinely new diagnostic

1335. NO HEARTBEAT GAMING WITH DIAGNOSTICS Repeatedly restating the same

1336. OWNER STATUS REMOTE DELIVERY OWNER_STATUS.md must be

Primary user promise: SAY WHAT YOU NEED → THE ASSISTANT FINDS / PREPARES
/ EXECUTES THE LEGITIMATE ACTION → THE USER ONLY SEES OR CONFIRMS WHAT
IS ACTUALLY NECESSARY.

The product must make clear that its value is not merely generating
text. Its value is connecting user intent to legitimate iPhone actions,
external services, bookings, purchases, documents, communication,
navigation, calendar, contacts and other supported capabilities.

Marketing may use the term “AI assistant” only if the released product
truthfully provides AI-assisted behavior. Do not imply that a paid AI
service is included if it is not.

1462. OPTIONAL USER-CONNECTED AI — BRING YOUR OWN AI

Add a provider-neutral optional AI connection layer.

The architecture must allow the user, where supported by provider terms
and technically legitimate, to connect a supported AI
provider/account/API credential or another authorized AI access
mechanism.

Requirements: - no single external AI vendor may be hard-wired as the
permanent architecture; - core non-AI/system actions must not
unnecessarily depend on a paid external model; - preserve the existing
v11 rule that the owner is not forced to fund every user’s external AI
usage; - user-connected AI must be clearly disclosed as user-provided
access where applicable; - never expose a user’s private AI credential
to another user; - store credentials only using an appropriate secure
mechanism; - do not put secret API keys in source code, app binary, logs
or analytics; - provider-specific capabilities, costs and limits must be
represented truthfully; - if a provider forbids a particular
credential-sharing or client-side pattern, use its supported
authorization flow or mark that connection path unavailable.

1463. VOICE-FIRST, NOT VOICE-ONLY

Voice is the primary interaction method, but not the exclusive one.

Always preserve: - typed natural-language input; - touch controls when
useful; - accessibility-compatible controls; - system-standard UI when
required by iOS; - user choice of interaction method.

Do not force the user through menus when a natural-language command is
enough. Do not force speech when typing or touch is more appropriate.

1464. CORE INTERACTION DECISION ENGINE

Before rendering UI or asking a question, determine:

1)  What is the user’s intent?
2)  What active context already resolves?
3)  Is the requested action permitted and executable now?
4)  Can it be completed safely without another question?
5)  Does the user need to see information?
6)  Does the user need to compare alternatives?
7)  Does the user need to select an item/person/time/place/variant?
8)  Does the action create a financial, contractual, privacy,
    destructive or irreversible consequence?
9)  Is authentication/unlock/system consent required?
10) Which exact controls are relevant to this task?

The system must then select a predefined, tested interaction pattern
appropriate to the intent. Do not generate arbitrary uncontrolled UI
from model output.

1465. DO, DON’T NARRATE — V12 REFINEMENT

Preserve the existing absolute DO, DON’T NARRATE rule.

If a command is: - clear; - safe; - authorized; - technically
executable; - not financially committing the user; - not materially
destructive; - not ambiguous; - not blocked by a required iOS/provider
confirmation;

perform it without unnecessary spoken or textual narration.

Do not say: - “Зараз зроблю”; - “Відкриваю”; - “Я знайшов”; -
“Починаю”; - “Зачекайте”; when the action itself is sufficient feedback.

A compact visual completion signal is allowed when useful.

This rule never overrides necessary payment, authentication, legal,
privacy, cancellation-fee, destructive-action or ambiguity handling.

1466. FULL-SCREEN UI IS CONDITIONAL, NOT DEFAULT

Do NOT open the app’s full-screen result UI for every command.

A full-screen result is required primarily when the user needs to: - see
visual information; - compare alternatives; - inspect an object; -
select an item; - review transaction details; - choose a
seat/table/time/variant; - edit a document; - authenticate; - perform a
provider checkout/payment handoff; - confirm a materially consequential
action.

Simple unambiguous actions should execute directly where iOS permits.

1467. FULL-SCREEN RESULT PATTERNS

Implement consistent full-screen result patterns for visual-selection
tasks.

PRODUCT: - image; - product name; - exact variant; - provider/seller; -
current price and currency; - known delivery cost/time; - availability
confidence; - relevant characteristics; - localized description where
allowed; - Buy/Open action.

RESTAURANT: - restaurant; - location; - useful rating/details where
legitimately available; - live available booking times only when
actually confirmed; - material booking conditions; - Reserve action.

ACCOMMODATION: - photos; - location/map; - requested dates; - guest
count; - price basis and known total; - availability state; -
cancellation/payment conditions; - Book action.

CAR RENTAL: - vehicle/model; - image; - pickup/return location; -
dates/times; - price basis; - availability state; - relevant rental
conditions; - Book action.

EVENT/TICKET: - event; - venue; - date/time; - ticket price; - seat/zone
availability when provider exposes it; - Buy Ticket action.

APPOINTMENT: - provider; - service; - specialist/master where
relevant; - available time; - price; - location; - Book Appointment
action.

1468. CONTEXT-SPECIFIC ACTIONS ONLY

Do not show the same large collection of buttons on every result.

Derive actions from the current object and legitimate provider
capabilities.

Examples: - product → Buy / Open; - restaurant → Reserve; -
accommodation → Book; - event → Buy Ticket; - appointment → Book; -
document → Save / Share / Edit when useful; - route → Start Route; -
calendar item → Add / Edit / Cancel as permitted.

If an action is unavailable for the current provider, do not display it
as functional.

1469. BOUNDED ACTIVE-TASK CONTEXT

Follow-up commands must apply to the current task without requiring the
user to repeat known details.

Examples: “Знайди квартиру у Львові завтра до 2500 гривень.” “Покажи
другу.” “На дві ночі.” “Забронювати.”

Or: “Скануй документ.” “Зроби одним PDF.” “Стисни.” “Назви Договір.”
“Відправ Олегу.”

Use active context only when the referent is sufficiently clear. If
there are multiple plausible contacts, objects, recipients or
transaction choices, ask only the minimum clarification required.

Do not convert active context into unlimited permanent personal memory.
Maintain separate concepts for: - current task context; - user-approved
history; - persistent assistant memory.

1470. IOS FAST INVOCATION — DEVICE-CAPABILITY AWARE

Expose legitimate fast invocation through all appropriate current iOS
mechanisms, including where supported: - App Intents; - Siri; -
Shortcuts; - Spotlight; - widgets; - Control Center/system surfaces
where legitimately available; - Action Button through a
user-configurable App Intent/Shortcut on supported iPhones; - Back Tap
through user-configured iOS accessibility/Shortcut behavior where
supported.

The application must NOT claim ownership of Action Button or Back Tap.
The user configures those system controls.

On devices without Action Button, including older iPhones, provide
legitimate alternatives without degrading core functionality.

1471. NO HIDDEN ALWAYS-LISTENING DESIGN

Do not design UniversalAssistant around an unrestricted hidden
continuously listening microphone.

Voice interaction begins through a legitimate invocation mechanism and
must respect current iOS microphone, speech, privacy and background
execution rules.

Do not fake wake-word behavior that iOS does not legitimately permit.

1472. LOCKED-DEVICE AND AUTHENTICATION TRUTH

Do not assume all actions can execute while the iPhone is locked.

For every capability, verify whether iOS or the provider requires: -
device unlock; - Face ID / Touch ID; - passcode; - account login; -
explicit system confirmation.

Ask for unlock/authentication only when required. Do not claim silent
execution where platform security prohibits it.

1473. DOCUMENT SCANNING — VOICE-DRIVEN WORKFLOW

Add document scanning as a first-class action capability.

Example: “Скануй документ.” → immediately enter the legitimate document
scanning/camera flow.

Then natural commands may include: - “Зроби одним PDF”; - “Збережи як
зображення”; - “Стисни”; - “Вирівняй”; - “Поверни сторінку”; - “Видали
третю сторінку”; - “Зміни порядок”; - “Об’єднай”; - “Розділи PDF”; -
“Розпізнай текст”; - “Зроби PDF з пошуком”; - “Переклади українською”; -
“Коротко поясни документ”; - “Що тут написано про оплату?”; - “Назви
файл Договір оренди”; - “Збережи”; - “Поділися”; - “Надрукуй”.

Do not force the user through a traditional scanner menu when speech
already identifies the desired operation.

1474. DOCUMENT IMAGE PROCESSING

Where technically appropriate, support: - page detection; - edge
detection; - crop; - perspective correction; - orientation correction; -
multi-page capture; - glare/shadow/contrast improvement where safe; -
OCR; - searchable PDF; - image-to-PDF; - PDF-to-image; - merge/split; -
page reorder; - page delete; - page rotation; - compression; -
annotation; - highlighting; - redaction; - signature placement where
legally and technically appropriate.

Never silently alter the semantic or legally significant content of a
document.

1475. DOCUMENT PRIVACY

Prefer on-device document processing where reasonably possible.

Do not upload passports, contracts, financial documents or other
sensitive scans to an external AI merely because server processing is
easier.

If an external service is necessary: - use only the minimum required
data; - obey user settings/consent; - document the data flow; - protect
data in transit and at rest; - apply retention/deletion rules; -
disclose relevant third-party processing as required.

1476. UNIVERSAL PROVIDER PLATFORM

All commerce, booking and external-service capabilities must use a
modular provider architecture.

Required conceptual path:

UniversalAssistant Core → Intent/Task Router → Provider Capability Layer
→ Provider Adapter → Official API / SDK / authorized partner interface /
allowed deep link / exact web handoff → verified result/action.

Do not hard-code third-party business logic into unrelated UI screens.

A new provider must be addable without rewriting the core application.

1477. CAPABILITY-BASED PROVIDER MODEL

Every provider adapter must declare its actual supported capabilities
independently, for example: - search; - details; - images; - current
price; - live availability; - booking; - booking modification; -
cancellation; - checkout; - payment handoff; - order creation; -
affiliate attribution; - booking/order status; - refund handoff; -
localization; - deep link.

Do not infer capabilities merely from a provider name. A seller API is
not automatically a buyer API. A documentation page is not proof of
production access. A mock is not proof of real integration.

1478. PROVIDER STATUS AND DEPTH

For every provider/category, use the existing v11 capability
contract/evidence contract.

Allowed practical states must distinguish at least: - production
verified; - implemented but awaiting real credentials/provider
approval; - partner application required; - owner action required; -
device test required; - provider restriction; - fallback only; -
unsupported with bounded negative proof.

Do not advertise an integration as live until required evidence is
achieved.

1479. RESTAURANT BOOKING

Support restaurant discovery and table reservation through legitimate
providers.

Priority provider candidates identified for feasibility/partner
investigation include: - Expirenza; - Table; - other
Ukrainian/international reservation platforms with legitimate access.

Target experience where supported: “Знайди грузинський ресторан сьогодні
на 19:00.” → show relevant restaurants; → show actually confirmed
available times/tables when provider supplies them; → user chooses; →
Reserve through the deepest legitimate provider path.

Do not claim direct booking through a provider unless that provider has
actually granted the necessary access.

1480. SHORT-TERM APARTMENTS AND HOTELS

Support accommodation discovery and booking.

Priority provider candidates include: - Dobovo; - Booking.com; - other
legitimate accommodation providers/partners.

Target experience: “Знайди квартиру у Львові на завтра до 2500 гривень.”
→ search connected sources; → normalize results; → show
photos/location/price/dates/availability; → Book through the deepest
legitimate supported path.

Distinguish: - instant confirmed booking; - booking request awaiting
host/provider confirmation; - availability not independently confirmed.

Never display these states as equivalent.

1481. CAR RENTAL

Support car rental discovery and booking where legitimate provider
access exists.

Candidate providers identified for investigation include: - Getmancar; -
other Ukrainian/international rental providers with authorized
partner/API/deep-link mechanisms.

Do not mark Bolt Drive or any other service as directly integrated
unless a legitimate consumer booking integration is actually available
and verified.

Target: “Знайди машину у Львові на три дні.” → available legitimate
providers/results; → car/photo/location/period/price/conditions; →
Book/Open exact provider flow.

1482. EVENTS AND TICKETS

Support tickets for: - concerts; - theatre; - stand-up; - shows; -
musicals; - children’s events; - festivals; - circus; - sports; -
exhibitions; - other legitimately supported events.

KARABAS is a priority Ukrainian partner candidate because partner
sales/integration mechanisms exist.

Where provider access permits: - discover events; - show
date/time/venue; - show actual ticket/zone/seat information; - hand off
or complete booking through authorized flow; - preserve partner
attribution.

1483. CINEMA

Support cinema discovery and ticket purchase where legitimate
integration is available.

Candidate services may include Ukrainian cinema chains/platforms such
as: - Multiplex; - Planeta Kino; - other providers.

Do not assume a public customer-facing website implies a public purchase
API.

If API access is unavailable but exact legitimate deep-link/web handoff
is permitted: → show useful session information only from
authorized/verified sources; → open the exact session/seat/purchase
destination.

1484. SALONS / BARBERS / SPA / APPOINTMENTS

Support appointment booking.

Altegio-compatible businesses are a priority integration category
because a formal integration API exists.

Target: “Запиши мене завтра на стрижку після 17:00.” → determine
location/preferences if known; → retrieve legitimate available times; →
show providers/masters/times/prices as available; → Book Appointment.

Support modification/cancellation only where provider capability and
rules permit.

1485. OTHER BOOKABLE SERVICES

The provider platform must be extensible to legitimate APIs for: -
beauty; - wellness; - SPA; - fitness facilities; - courts/pools; -
activities; - attractions; - excursions; - travel experiences; -
transfers; - repair/service appointments; - other bookable real-world
services.

Do NOT automatically add unsupported categories to the released UI
merely because the architecture can represent them.

1486. TAXI EXCLUSION FROM CONFIRMED MARKETING

Do not advertise third-party taxi ordering as a confirmed
UniversalAssistant integration unless a legitimate consumer booking
API/partner mechanism is later verified.

Existing generic navigation/open-app capabilities may remain if already
legitimate.

No fake taxi booking. No simulated tap automation in another taxi app.
No unverified taxi price/ETA.

1487. SHOPPING AGGREGATION

Support product discovery from legitimate connected marketplaces/stores.

Priority candidates include: - Amazon; - eBay; - AliExpress; - Temu; -
Prom.ua; - other stores/marketplaces with legitimate APIs, affiliate
feeds, partner links or exact deep links.

Provider capabilities differ.

Do not claim that all of these providers expose a buyer checkout API.
Implement each at the deepest legitimate level actually available.

1488. SHOPPING PROVIDER-SPECIFIC TRUTH

The system must distinguish provider paths.

Examples of possible legitimate paths: - API-based search/details; -
affiliate product feeds; - provider-hosted checkout; - exact product
deep link; - exact affiliate link; - authorized SDK.

Prom.ua seller/merchant APIs must not be misrepresented as a
marketplace-wide buyer API unless separate authorized access is
obtained.

Temu, AliExpress, Amazon, eBay and others must each be implemented only
according to their current official partner/API rules at implementation
time.

1489. LOCALIZATION OF EXTERNAL CONTENT

UniversalAssistant must present its own UI in the user’s selected
language.

External descriptive content may be translated to the user’s language
where allowed.

However, never silently modify transaction-critical fields: - price; -
currency; - model; - SKU; - size; - color/variant identity; -
quantity; - dates; - times; - seller/provider identity; - cancellation
terms; - refund terms; - legal/contractual terms.

Where machine translation could affect a material transaction decision,
preserve access to the original wording.

1490. MULTI-PROVIDER SEARCH NORMALIZATION

Normalize provider results into a coherent common display without
erasing source truth.

Every normalized result must retain: - source provider; - retrieval
timestamp where relevant; - freshness/verification state; - original
identifier/link; - price basis; - availability basis; - known mandatory
fees; - provider-specific restrictions.

Never invent missing fields merely to make cards look uniform.

1491. AVAILABILITY TRUTH

Use explicit availability states.

Examples: - LIVE_CONFIRMED; - PROVIDER_CONFIRMED; - REQUEST_REQUIRED; -
CACHED_RECENT; - UNKNOWN; - UNAVAILABLE.

Do not show “available” when the source only provides an old listing or
an unconfirmed request flow.

Never fake: - free tables; - apartment availability; - vehicle
availability; - ticket seats; - salon time slots; - product stock.

1492. PRICE COMPARISON TRUTH

Do not compare raw headline prices as if they were always equivalent.

Where data is available, account for: - exact product variant; -
quantity; - currency; - delivery; - mandatory service fees; - known
taxes; - stay length; - guest count; - rental duration; - ticket
category; - required deposits; - other mandatory charges.

Distinguish: LISTED PRICE from KNOWN/ESTIMATED TOTAL.

Do not call an offer “cheapest” unless the compared values are
materially comparable.

1493. THIRD-PARTY PAYMENT ARCHITECTURE

For third-party physical goods and real-world services,
UniversalAssistant must NOT by default become the merchant/seller and
must NOT unnecessarily receive the full customer payment into its own
account.

Preferred transaction structure:

User → UniversalAssistant discovery/selection → legitimate provider
checkout/payment flow → money for the product/service goes directly to
the provider/merchant → UniversalAssistant separately receives
contractual affiliate/referral/agency commission where applicable.

Do not design this to “avoid taxes.” Design it to correctly separate
third-party transaction money from UniversalAssistant’s own revenue and
reduce unnecessary payment-regulatory/accounting complexity lawfully.

1494. UNIVERSALASSISTANT OWN PAYMENTS ARE SEPARATE

Payments for UniversalAssistant’s own digital product, subscription or
digital features must follow current Apple rules and applicable law.

Do not confuse: A) payment for UniversalAssistant itself; with B)
payment for a third-party physical product or real-world service.

Codex must verify current App Store rules before implementing final
payment flows.

1495. BUY / BOOK / PAY DESTINATION PRIORITY

For a selected third-party item/service, use the deepest officially
permitted transaction destination.

Possible legitimate destinations include: - authorized provider API
transaction; - provider SDK; - provider-hosted checkout; - provider app
deep link; - exact product/service/session/booking URL; - exact
affiliate/partner link.

Do not assume API checkout is always preferable. Provider rules decide
what is legitimate.

Never dump the user on a generic homepage when a legitimate exact
destination exists.

1496. FINANCIAL CONFIRMATION

Before a materially financially committing action, show the information
necessary for an informed confirmation where applicable: - exact
selected item/service; - quantity; - amount; - currency; - mandatory
known fees; - cancellation/refund consequences; - relevant date/time.

Final payment authorization must occur through the legitimate
provider/bank/payment mechanism.

UniversalAssistant must not impersonate bank/provider authorization.

Do not store raw payment card credentials.

1497. PARTNER / AFFILIATE MONETIZATION

Implement partner monetization as a first-class business capability.

Possible legitimate revenue: - affiliate commission; - referral
commission; - agency commission; - contractual partner remuneration.

Build a provider-neutral attribution layer capable of storing, where
legally and contractually permitted: - provider; - partner ID; -
campaign/source; - referral/click identifier; - order/booking
attribution identifier; - commission status; - commission amount if
actually supplied; - currency; - timestamps.

Never invent a commission amount.

1498. COMMISSION AND USER PAYMENT SEPARATION

Do not treat the full purchase price of a third-party good/service as
UniversalAssistant revenue merely because UniversalAssistant initiated
the referral.

Keep: - user payment to merchant/provider; - UniversalAssistant
affiliate/agency revenue; - UniversalAssistant own subscription revenue

separate in data model, accounting events and analytics.

Any final tax/accounting implementation must be validated against the
actual legal entity/jurisdiction before production release.

1499. ORGANIC VS COMMERCIAL RANKING

Affiliate commission must not silently determine normal result ranking.

Organic ranking should primarily reflect the user’s request and relevant
factors such as: - constraint match; - availability; - total cost; -
distance; - rating; - delivery; - dates/times; - explicit user
preferences.

If a commercial agreement changes placement, support clear
sponsored/paid labeling as required.

Do not present a paid placement as objectively “best” without
disclosure.

1500. BOOKING MODIFICATION / CANCELLATION

Where a provider legitimately supports it, allow natural-language
commands such as: - “Скасуй бронювання”; - “Перенеси на 20:00”; - “Зміни
дату”; - “Зміни кількість гостей”; - “Покажи умови скасування”.

Before a change that can create a fee, loss of deposit or other material
consequence: → show the consequence; → obtain necessary confirmation.

1501. REFUND HANDOFF

If the provider/merchant controls the refund, UniversalAssistant must
not pretend that UniversalAssistant itself has refunded the money.

Use: - official refund API where authorized; - official provider refund
flow; - exact support/order handoff.

Show truthful state: REQUESTED / PROVIDER_PROCESSING / REFUNDED only
when verified.

1502. NO UNAUTHORIZED SCRAPING OR PRIVATE-API AUTOMATION

Absence of a public API does NOT authorize: - protected scraping; -
reverse engineering of private consumer APIs; - credential
interception; - simulated taps in another app; - CAPTCHA bypass; -
checkout imitation; - payment interception; - unauthorized account
automation.

Use only official or legitimately permitted mechanisms.

A normal publicly accessible exact web/deep-link handoff may be used
where provider terms permit it.

1503. API AND PARTNER SECRET SECURITY

All provider secrets must follow least privilege.

Never hard-code: - secret API keys; - client secrets; - affiliate
private secrets; - server tokens into the iOS binary.

Where required, use secure backend handling.

Support: - scoped credentials; - token expiration; - refresh; -
revocation; - rotation; - secure transport; - redacted logs; - secret
separation by environment.

1504. PROVIDER FAILURE ISOLATION

One provider failure must not break the whole task.

For multi-provider search: - call providers concurrently where
appropriate; - apply bounded timeouts; - isolate failures; - return
valid results already available; - allow safe late-result merge where
useful; - never keep the user behind an infinite spinner; - never
fabricate missing results.

Preserve existing v11 NEVER-FREEZE rules.

1505. IOS PERMISSIONS — JUST IN TIME

Do not request all permissions at first launch.

Request permission when the user invokes a capability that actually
needs it.

Examples: - microphone/speech → voice command; - camera →
scanning/capture; - photos/files → selected media/document operation; -
contacts → recipient/contact action; - calendar/reminders →
corresponding action; - location → location-dependent action.

Respect denial. Provide legitimate fallback when possible. Do not
repeatedly nag after a clear denial.

1506. IPHONE SYSTEM INTEGRATION

Integrate deeply with legitimate iPhone capabilities where permitted,
including applicable frameworks for: - Calendar; - Reminders; -
Contacts; - Files; - Photos; - Camera/document capture; -
Maps/navigation; - system share sheet; - notifications; - App
Intents/Shortcuts; - Spotlight; - widgets/system invocation surfaces.

Examples: “Запиши зустріч завтра о 15:00.” → create the correct calendar
event when unambiguous and authorized.

“Нагадай завтра о 9:00.” → create reminder.

“Відправ цей PDF Олегу.” → resolve current document and recipient;
clarify only real ambiguity; use legitimate share/message/mail flow.

Do not claim direct control of an app/system feature that iOS does not
grant.

1507. MARKETING PRIORITY — SHOW ACTIONS FIRST

The first marketing impression must demonstrate concrete useful actions,
not generic AI chat.

Priority advertising demonstrations should include only capabilities
actually available in the released build, such as:

-   restaurant → find → real availability → reserve;
-   apartment/hotel → find → compare → book;
-   event → find → select → buy ticket;
-   salon/barber/SPA → free time → book;
-   product → compare across legitimate connected stores → buy;
-   car rental → availability → book where legitimate integration
    exists;
-   document → scan → PDF → save/share;
-   calendar/reminders/iPhone actions.

Core marketing idea: ONE AI ASSISTANT FOR REAL ACTIONS ON IPHONE.

Do not advertise a provider as integrated merely because its logo/name
appears in development plans.

1508. APP STORE DESCRIPTION TRUTH

The App Store name/subtitle/description may use “AI” only in a truthful
manner.

If users connect their own AI provider: - disclose this clearly before
they incur external provider costs; - do not imply unlimited AI is
included if it is not; - explain which core functions work without an
external paid AI connection; - follow current Apple metadata and
disclosure rules.

Never use misleading screenshots or descriptions.

1509. RELEASE ACCEPTANCE FOR EACH NEW V12 CAPABILITY

A v12 capability is NOT DONE because: - UI exists; - adapter compiles; -
mock data renders; - a provider website was opened; - documentation says
an API exists.

For each capability, apply the v11 evidence ladder and capability
acceptance contract.

At minimum, trace: USER INTENT → ROUTER → CORRECT PROVIDER/SYSTEM PATH →
REAL DATA/ACTION OR TRUTHFUL BLOCKER/FALLBACK → OBSERVABLE RESULT →
ERROR/FALLBACK BEHAVIOR → REQUIRED DEVICE/PRODUCTION-LIKE TEST.

If credentials, partner approval, Apple enrollment or another external
prerequisite is missing: - implement only what can be legitimately
implemented; - record the exact blocker; - do not fake completion; -
continue with independent work that is not blocked.

Where any earlier v1–v12 wording conflicts with a v13 rule below, the
explicit v13 rule SUPERSEDES the earlier wording, subject always to
current law, Apple rules, provider rules, safety and verified technical
truth.

The following earlier concepts are specifically superseded where
conflicting: - “base AI mode” wording: the Base Mode is NOT a hosted
paid AI service; - “future Free/Premium only” wording: v13 defines the
launch entitlement model; - mandatory preparation of a Family tier:
Family tier is NOT a V1 requirement and belongs only in backlog unless
the owner later approves it; - broad internal Notes/shopping-list
duplication: use SYSTEM-FIRST routing and do not duplicate iPhone system
capabilities without a proven product need; - app-first handoff
assumptions: use verified exact-result web/app/provider flow rules
below; - any UI sketch content that conflicts with the approved v13 UI
rules: v13 textual UI rules are authoritative. - rigid “zero retry /
prohibited path change” process wording: use evidence-based, bounded
engineering judgment. Avoid unchanged repetition, but permit a bounded
verification retry or path change when transient conditions, diagnostic
uncertainty, new evidence, measured benefit, or a simpler equal/better
solution justifies it.

1511. CORE PRODUCT BEHAVIOR — USER-INTENT ONLY UniversalAssistant must
      do what the user asked and must not add unsolicited advice,
      recommendations, comparisons, upsells, AI prompts, alternate
      scenarios or extra actions except when required for safety, truth,
      minimal clarification or a truthful fallback when the exact result
      cannot be completed.

1512. DO, DON’T NARRATE — RECONFIRMED For clear legitimate actions,
      execute with minimal narration. Do not say “I found it”, “I am
      opening”, “I will now…” unless such narration materially helps the
      user.

1513. NO UNSOLICITED COMPARISON Do not compare products/services unless
      the user explicitly asks to compare or the exact task inherently
      requires comparison such as “find the cheapest”.

1514. NO UNSOLICITED “SMART” ADVICE Do not display obvious or low-value
      advice such as “this one is 500 UAH cheaper” merely to appear
      intelligent. If the user asks for advice, use only verified
      materially relevant distinctions; if the evidence is insufficient,
      do not invent a recommendation.

1515. BASE MODE IS NOT HOSTED AI The default Base Mode is
      UniversalAssistant’s own orchestration stack: voice/text input →
      local Structured Command Engine → iPhone/system/provider actions.
      It must not require owner-funded external LLM inference for
      routine structured tasks.

1516. OPTIONAL USER-CONNECTED AI REMAINS OPTIONAL A user may connect a
      supported AI provider where legitimate. The connected AI is an
      optional reasoning/analysis component and does not replace
      UniversalAssistant entitlements or unlock Premium automatically.

1517. NO PAID AI FOR ROUTINE STRUCTURED WORK Do not spend paid
      external-AI tokens on tasks reliably handled by local parsing,
      deterministic logic, system frameworks, structured APIs,
      arithmetic, currency conversion, localization of fixed UI strings,
      routing or simple provider normalization.

1518. STRUCTURED COMMAND ENGINE — PRODUCTION CORE Implement a
      production-grade local Structured Command Engine, not a few
      hard-coded phrases. It must parse natural commands into intent,
      entities, constraints, priorities, context and requested actions.

1519. STRUCTURED COMMAND EXAMPLE Example input: “Baldinini, men’s,
      black, leather, size 41, latest collection, up to 12000” must
      normalize to fields such as brand, category, gender, color,
      material, size, collection constraint and max_price without
      external paid AI.

1520. STRUCTURED COMMAND LANGUAGE COVERAGE Support Ukrainian, Russian,
      English, German and French across command parsing with
      normalization of inflections, synonyms, numbers, dates, times,
      currencies, units, brands, locations and common speech-recognition
      variants.

1521. STRUCTURED FOLLOW-UP CONTEXT Short follow-ups such as “the
      second”, “open it”, “buy this”, “tomorrow instead”, “cheaper”,
      “through Waze” must resolve against the current structured task
      context without re-running unrelated work.

1522. CONSTRAINT CLASSIFICATION The local engine must distinguish hard
      constraints from soft preferences where the wording permits, and
      must never silently relax a hard constraint.

1523. ALTERNATIVE EXPLANATION WITHOUT AI When an exact match is
      unavailable, compute and show the specific difference locally,
      e.g. “900 UAH more”, “2025 collection”, “dark blue”, rather than a
      vague “not exact”.

1524. NO DEAD-END “NO EXACT MATCH” Do not stop at “No exact option”. If
      relevant alternatives exist, show them immediately and state
      exactly how each differs from the request.

1525. ALTERNATIVE RANKING Rank alternatives by smallest meaningful
      deviation from the user’s intent using domain-aware priorities.
      Example: wrong shoe size is normally a more serious deviation than
      a small price increase.

1526. HONEST ABSENCE WORDING Do not claim “nowhere available” unless
      proven. Prefer wording equivalent to “No confirmed availability
      found in the checked sources” when exhaustive absence cannot be
      established.

1527. MULTI-SOURCE CASCADE For commerce/service discovery, continue from
      exact local result → other nearby/city results → legitimate online
      stores/marketplaces → other relevant alternatives, bounded by
      time/cost and provider constraints.

1528. RATIONAL INTERNAL SELECTION If the user does not explicitly ask
      for “cheapest”, do not blindly return the first offer. Internally
      avoid obviously poor equivalent offers when better confirmed
      equivalent offers are available, but do not narrate criteria the
      user did not ask about.

1529. EXPLICIT USER CRITERION HAS PRIORITY If the user explicitly says
      cheapest, nearest, fastest, specific merchant, specific delivery
      method, exact date/time or another criterion, that criterion
      controls ranking/selection subject to truth and safety.

1530. RESULT UI — UNIVERSAL STRUCTURE Use a universal visual structure
      but domain-specific fields: media/photo → primary facts → verified
      price/availability/status → source/provider → relevant action.

1531. RESULT LIST SIZE Prefer a concise useful set (typically 3–5 top
      relevant results when selection is required) rather than dozens of
      noisy results, while allowing expansion when requested.

1532. DIRECT ACTION FROM RESULT CARD When enough information is already
      visible, allow the user to act directly from the result card
      without forcing a detail page first.

1533. DETAIL VIEW ONLY WHEN USEFUL Open a detail view when the user
      wants more information or when the domain materially benefits from
      photos, terms, map, cancellation rules or other detail.

1534. APPROVED MAIN SCREEN The approved main screen is premium, clean
      and technology-focused: one large central branded
      microphone/control, status text such as “Listening…” when
      appropriate, text entry at the bottom labeled “Або напишіть”, left
      capabilities menu and right settings control. Do not add a second
      microphone or redundant “say/hello” prompts.

1535. APPROVED BOTTOM NAVIGATION Primary persistent navigation: Home |
      My Tasks | Favorites. Do not use unread-count anxiety badges for
      ordinary items.

1536. LEFT CAPABILITIES MENU Left menu provides optional navigation such
      as Recent/Frequent, Housing, Food, Shopping, Transport,
      Entertainment, Services, Documents, My Tasks, History. Normal use
      must never require browsing these categories; natural command
      routing remains primary.

1537. RIGHT SETTINGS STRUCTURE Settings must include, as applicable:
      Base Mode status, Connect your AI, Connected AI (only when
      present), Language, Appearance, Voice & Interaction,
      Personalization, iPhone Permissions, UniversalAssistant
      Subscription, Privacy & Data, About.

1538. APPEARANCE One Appearance section contains System/Automatic, Dark,
      Light, accent color, animation level and related display
      preferences. Default should respect the iPhone system theme unless
      overridden by the user.

1539. LIGHT THEME Light theme is the same product design, not a second
      product. Preserve the same layout and branded accent while using a
      premium light neutral background, readable dark text and clean
      light cards.

1540. VOICE & INTERACTION SETTINGS Include only useful real controls
      such as voice responses on/off, supported voice choice, speech
      rate, start/end listening sounds and haptics, and permitted
      fast-listening behavior. Do not invent unsupported microphone
      controls.

1541. PERSONALIZATION Personalization may store user-approved useful
      preferences such as Home/Work, preferred currency, clothing/shoe
      sizes, favorite places/stores/restaurants, preferred navigation
      service and explicitly confirmed recurring preferences.

1542. PERSONALIZATION MUST NOT BE FORCED Do not require the user to fill
      a profile up front. Where useful, ask once in context,
      e.g. “Remember size 41?” and store only after explicit
      confirmation.

1543. CONTACTS ARE SYSTEM CONTACTS Do not create a duplicate contact
      database. Use authorized iPhone Contacts and store only minimal
      assistant-owned aliases/metadata when useful and permitted.

1544. SYSTEM-FIRST TASK ROUTING Do not rebuild iPhone Calendar,
      Reminders, Contacts or other standard system capabilities. Route
      structured actions to the legitimate system framework where
      available.

1545. COMBINED DICTATION ROUTING A single dictation may generate several
      destination actions, e.g. meeting → Calendar, reminder/alert →
      permitted system mechanism, address → event metadata. Parse once,
      route each sub-action correctly, avoid duplicate copies.

1546. NOTES / LISTS SUPERSESSION Earlier broad “internal Notes/shopping
      lists by default” wording is superseded. First use legitimate
      iOS/system storage or allowed handoff where available. Build
      assistant-owned storage only when a real requirement cannot be met
      otherwise and after proving that duplication is justified.

1547. MY TASKS ROLE “My Tasks” is a first-class user surface, not a
      settings item. It should aggregate what the user needs now: active
      external bookings/orders when known, user-requested watches,
      unfinished assistant tasks, relevant upcoming items and other
      assistant-owned state.

1548. MY TASKS DOES NOT DUPLICATE SYSTEM DATA Where Calendar/Reminders
      data is displayed in My Tasks, read it from authorized system
      sources rather than duplicating full records into the
      UniversalAssistant server database.

1549. CALM ASSISTANT Do not create anxiety through persistent unread
      indicators. Ordinary updates must not leave red badges or “17
      unread” counters that require clearing.

1550. ATTENTION IS ACTION-BASED, NOT READ-BASED Highlight only items
      requiring timely user action. Do not keep an item visually urgent
      merely because the user has not opened it.

1551. FAVORITES VS WATCHES Favorites are passive saved references.
      Watches are active server/user-requested monitoring tasks. Never
      turn Favorites into hidden background monitoring.

1552. FAVORITES MINIMAL STORAGE For Favorites, store a minimal stable
      provider/item/place/listing/event/service reference plus minimal
      local display data. Do not copy full third-party pages.

1553. FAVORITES FRESHNESS When Favorites is opened, refresh mutable
      fields such as price, stock or listing status using a bounded
      legitimate path. If freshness cannot be confirmed, say so.

1554. WATCHES REQUIRE USER INTENT Create a watch only when the user
      explicitly asks for monitoring such as price threshold, size
      availability, table availability, housing availability or ticket
      availability.

1555. WATCH NOTIFICATIONS Notify only on a meaningful new
      condition/event and deduplicate repeated unchanged states.

1556. WATCH SERVER EFFICIENCY Do not poll separately for identical
      conditions for thousands of users. Deduplicate/group equivalent
      checks where legitimate, cache safe shared results and respect
      provider rate limits/terms.

1557. WATCH DATA MINIMIZATION Store only the minimal structured data
      needed to evaluate the watch, e.g. provider/item ID,
      constraint/threshold, expiry, task/user technical identifiers. Do
      not store full audio, full conversation or continuous GPS history
      without need.

1558. WATCH EXPIRATION Watches must have explicit
      validity/expiry/cancellation handling and must not run forever
      after they become irrelevant.

1559. NOTIFICATION CONTENT A notification should answer: what changed,
      why it matters to the user’s requested condition, and what action
      is available now.

1560. NO AUTOMATIC MARKETING NOTIFICATIONS Do not turn
      watches/favorites/history into marketing push. User-requested
      alerts and genuinely necessary transactional/time-sensitive alerts
      only, subject to settings and law.

1561. IMPORTANT ACTION CONFIRMATION PERSISTENCE Small confirmations may
      disappear. Confirmed important external actions such as bookings,
      orders or appointments must remain retrievable in My Tasks when
      UniversalAssistant has verified state.

1562. NEVER CLAIM PURCHASE/BOOKING WITHOUT PROOF Show “Purchased”,
      “Booked”, “Sent”, “Refunded” or equivalent only when the relevant
      system/provider confirms it. Otherwise show the truthful
      intermediate state.

1563. ORDER/BOOKING STATUS ON DEMAND Do not become a full-time duplicate
      tracker by default. When the user asks “Where is my order?”, use a
      legitimate provider account/API/order ID/tracking number source to
      fetch the status if available.

1564. ACTIVE STATUS WATCH ONLY WHEN ASKED If the user says “Notify me
      when it arrives”, create an explicit watch. Otherwise do not
      continuously poll simply because an order exists.

1565. PROVIDER STATUS SOURCE RULE Exact order/parcel status requires a
      verified source such as official API, authorized account
      connection, official tracking identifier or provider page. Do not
      infer delivery status.

1566. PARTNER ATTRIBUTION MUST SURVIVE HANDOFF When multiple equally
      legitimate paths exist, prefer the path that preserves
      UniversalAssistant’s valid affiliate/referral attribution without
      degrading user intent or user value.

1567. WEB-FIRST EXACT RESULT FLOW For third-party commerce/service
      results, prefer showing the exact web result in a controlled
      legitimate UniversalAssistant web/system browser flow when this
      preserves exact context and avoids installed-app universal-link
      loss.

1568. APP HANDOFF ONLY WHEN VERIFIED Use app handoff before final
      checkout only when the exact deep/universal link is verified to
      preserve the requested product/context and, where applicable,
      valid partner attribution.

1569. CHECKOUT/AUTH PROVIDER RULES WIN Login, OAuth, checkout and
      payment must use the provider/Apple-approved mechanism required by
      the service, even when that means leaving the embedded flow for a
      system browser, provider app, SDK or authorization session.

1570. DESTINATION VERIFICATION Before exposing Buy/Book/Open/Pay, verify
      where technically reasonable that the destination is valid,
      specific, not a known 403/404, and does not unexpectedly dump the
      user on a generic homepage or lose critical filters.

1571. FAILED DESTINATION FALLBACK If the preferred destination fails,
      automatically try the next legitimate exact path. Do not show raw
      technical errors if a working fallback exists.

1572. PARTNER MONETIZATION STARTS PRE-LAUNCH Do not postpone affiliate
      monetization until after user growth. Prepare applications and
      integrations during development.

1573. PARTNER PRE-LAUNCH ASSETS Prepare a legitimate UniversalAssistant
      landing/site, product description, privacy/legal pages,
      contact/business information and demo/screenshots where required
      for partner applications.

1574. PARTNER PROGRAM APPLICATIONS Apply during development to relevant
      affiliate networks and direct merchant/service programs.
      Automatically approved programs may be activated immediately;
      manually reviewed programs proceed in parallel.

1575. PROVIDER-NEUTRAL AFFILIATE LAYER Implement one modular
      Affiliate/Attribution Layer. New networks/merchants must be added
      via adapter/configuration rather than widespread core changes.

1576. PARTNER STATUS REGISTRY Maintain explicit status such as CANDIDATE
      → APPLICATION_REQUIRED → APPLIED → APPROVED → CREDENTIALS_RECEIVED
      → IMPLEMENTED → TEST_VERIFIED → PRODUCTION_VERIFIED →
      EARNING_VERIFIED.

1577. EARNING VERIFIED MEANING Mark EARNING_VERIFIED only after real or
      officially supported test evidence demonstrates
      attribution/conversion tracking. A click is not a commission.

1578. COMMISSION TRUTH Never invent commission percentage, amount or
      payment terms. Use only current contract/dashboard/API data.

1579. COMMISSION DOES NOT CONTROL ORGANIC RESULT Affiliate economics may
      not secretly make a materially worse result rank above a better
      match. User intent and legitimate result quality remain primary.

1580. PARTNER TRANSACTIONS AND FREE LIMITS Do not unnecessarily block
      completion of an already-started legitimate partner
      purchase/booking because a Free usage allowance was reached, where
      product policy permits and no unacceptable cost/safety issue
      exists.

1581. LIGHTWEIGHT GLOBAL RULE UniversalAssistant must be lightweight in
      CPU, RAM, battery, storage, network use and number of execution
      steps.

1582. NO WASTED WORK Avoid repeated parsing, duplicated provider calls,
      repeated checking of already-established facts, unnecessary serial
      requests, unnecessary AI calls and unnecessary background work.

1583. PARSE ONCE For a structured command, parse the intent once and
      pass the normalized result through the pipeline rather than
      repeatedly re-parsing the same natural-language command.

1584. PARALLELIZE INDEPENDENT NETWORK WORK Run independent provider
      calls in parallel where safe and beneficial. Do not make the user
      wait for sequential work that can be concurrent.

1585. STOP WHEN ENOUGH Once the user’s requested result is sufficiently
      satisfied, cancel or deprioritize unnecessary remaining work
      unless background completion is required for correctness.

1586. LAZY LOAD Load heavy modules/resources only when needed. Keep
      startup and the main voice/text path minimal.

1587. BOUNDED MEMORY/CACHE Use bounded caches and avoid retaining large
      histories/objects in memory. Persist only necessary state.

1588. FIRST USEFUL RESULT Measure time-to-first-useful-result for major
      flows. Primary text/price/availability/action should render before
      heavy images or secondary metadata.

1589. IPHONE SE 2 PERFORMANCE TARGET Performance, memory and interaction
      tests must include the older supported hardware target such as
      iPhone SE 2 if it remains in the chosen minimum support matrix.

1590. WEAK-NETWORK RESILIENCE Do not freeze waiting for a heavy
      page/provider. Use progressive rendering and bounded timeouts;
      continue with valid partial state when possible.

1591. SAFE RESUME / CHECKPOINTING For long/multi-step tasks, locally
      persist minimal checkpoint state sufficient to resume after
      background termination, crash, memory pressure or restart.

1592. NEVER AUTO-RESUME IRREVERSIBLE FINANCIAL ACTION Never
      automatically re-submit payment, paid booking, penalty
      cancellation or another materially irreversible action after
      resume without new explicit user confirmation.

1593. IDEMPOTENCY Use provider-supported idempotency/order/booking
      identifiers to avoid duplicated actions on retries/resume where
      available.

1594. CODEBASE HYGIENE Do not leave dead parallel implementations,
      obsolete fallbacks or temporary duplicate components after a path
      is replaced and verified. Preserve Git history, not dead runtime
      code.

1595. MODULAR PROVIDER EVOLUTION New merchants/services/providers should
      integrate through clear adapters/capability configuration without
      rewriting the orchestration core.

1596. BUNDLE/DEPENDENCY HYGIENE Track bundle size, startup time,
      dependency weight, dead code and duplicate network paths.
      Significant dependencies require measured justification.

1597. ACCOUNT REQUIRED, BUT NOT FIRST-SCREEN REQUIRED UniversalAssistant
      has an account model for sync, server watches, entitlement and
      recovery, but the user may try the product before registration.

1598. SIGN IN METHODS Use Sign in with Apple as a primary
      iPhone-appropriate method and optionally Google where current App
      Store rules and implementation allow. Follow current Apple
      account/sign-in requirements.

1599. GUEST TRIAL Launch configuration: Guest may perform 15 completed
      user actions OR use the app for 7 days, whichever comes first,
      before registration is required for further ordinary use.

1600. GUEST IDENTIFIER PRIVACY Do not use prohibited or invasive device
      fingerprinting to enforce guest limits. Use legitimate
      app/install/session identifiers and server/local mechanisms
      consistent with current Apple/privacy rules.

1601. FREE REGISTERED ALLOWANCE Launch configuration: registered Free
      users receive 30 ordinary user actions per rolling/configured
      7-day entitlement cycle.

1602. FREE RESET At the next 7-day cycle boundary, the Free allowance
      resets to 30. Unused actions do not accumulate unless the owner
      later changes policy.

1603. ONE ACTION DEFINITION One action is one completed user
      task/intent, not the number of internal API calls, screens,
      provider checks or sub-operations required to fulfill it.

1604. FOLLOW-UPS DO NOT BECOME A TAXIMETER Short follow-ups and
      completion steps within the same active task, such as “second
      one”, “open it”, “buy”, “book”, do not consume a new ordinary
      action unless they start a genuinely new independent task.

1605. COMPOUND TASK COUNTS AS ONE WHEN COHERENT A natural compound
      command such as “create a meeting tomorrow at 15:00 and remind me
      an hour before” counts as one user task even if routed to multiple
      system mechanisms.

1606. PREMIUM ENTITLEMENT Premium removes the ordinary Free action
      ceiling for normal human use and unlocks designated
      premium/server-intensive capabilities, subject to fair-use/abuse
      protections.

1607. DO NOT MARKET PREMIUM AS ABSOLUTELY UNLIMITED Use truthful wording
      equivalent to “no ordinary action limit” if technical rate/abuse
      limits exist.

1608. PREMIUM CAPABILITY EXAMPLES Premium may include server watches,
      more/advanced automation, expanded document workflows, broader
      synchronization and other capabilities that create recurring
      product/server value, as defined by current product policy.

1609. USER-CONNECTED AI DOES NOT BYPASS ENTITLEMENTS Free +
      user-connected AI remains Free with Free UniversalAssistant
      limits. Premium + user-connected AI receives Premium
      UniversalAssistant capabilities while the user bears their AI
      provider costs.

1610. LAUNCH PRICE CONFIGURATION — NOT PERMANENT Current
      launch/reference configuration: Monthly $4.99 and Annual $39.99.
      These values are NOT frozen/permanent product prices.

1611. PRICING MUST BE CONFIGURABLE Do not hard-code commercial prices in
      business logic. Storefront pricing must use legitimate App
      Store/StoreKit configuration and product policy must support
      owner-approved future changes.

1612. FUTURE PRICE REVIEW Price may increase or otherwise change based
      on real product value, capability growth, AI/automation evolution,
      demand, retention/conversion, server/API costs, partner revenue
      and market conditions, subject to current Apple rules and correct
      handling of existing subscribers.

1613. PAYWALL BEHAVIOR Do not spam users with Premium banners. Near
      exhaustion, a calm one-time remaining-usage indicator may appear.
      After allowance is exhausted, the next new ordinary task may show
      Premium or wait/reset options.

1614. NEVER BLOCK OWNED DATA BEHIND PAYWALL My Tasks, existing
      bookings/order references, Favorites and user-owned data must
      remain accessible after downgrade, subject to legitimate
      read/export and privacy rules.

1615. ACCOUNT DELETION / DATA RIGHTS Account creation requires in-app
      account deletion initiation and appropriate data deletion/export
      controls consistent with current Apple/law requirements.

1616. PHONE-WIDE APP ORCHESTRATION UniversalAssistant must attempt the
      deepest legitimate integration with relevant installed/system apps
      through official iOS/app mechanisms, without claiming universal
      control over all apps.

1617. APP CAPABILITY MATRIX For important apps/categories maintain
      capabilities such as OPEN_APP, OPEN_EXACT_CONTEXT, SEARCH, READ,
      CREATE, UPDATE, SEND, PLAY, PAUSE, NAVIGATE, BOOK, ORDER,
      PAY/HANDOFF, APP_INTENT, SHORTCUT, DEEP_LINK, UNIVERSAL_LINK, SDK,
      API, AUTH_REQUIRED, LIMITATIONS and TEST_STATUS.

1618. MUSIC/MEDIA DOMAIN IS MANDATORY Audit and implement the deepest
      legitimate practical integration for Apple Music, Spotify and
      other relevant media services available in the launch market.

1619. MEDIA INTENTS Where supported, enable commands such as
      play/search/open exact artist/album/playlist/track, pause/resume,
      next/previous and open the provider, using legitimate integration
      only.

1620. MEDIA DOES NOT REQUIRE UNIVERSALASSISTANT TO STAY HEAVY IN
      BACKGROUND After UniversalAssistant legitimately starts media
      playback in a provider/system player, playback should continue
      through that player without UniversalAssistant maintaining a heavy
      continuous background process.

1621. MANAGED MEDIA PAUSE/RESUME DURING NEW QUERY If media playback was
      started/controlled through UniversalAssistant and the integration
      legitimately permits control, a new UniversalAssistant voice query
      should pause the managed playback at its current position during
      listening/voice response, then resume from the same position
      unless the new user command changes the media intent.

1622. INDEPENDENT MEDIA PLAYBACK For media not launched/controlled by
      UniversalAssistant, do not assume control rights. Use only
      legitimate iOS audio-session interruption/ducking/mixing behavior.

1623. CALL/COMMUNICATION AUDIO PRIORITY Active system/FaceTime/VoIP
      calls take priority over UniversalAssistant narration. Correctly
      yield audio and preserve safe task state.

1624. SYSTEM QUICK ACTIONS For simple system commands, use the shortest
      current legitimate iOS mechanism instead of rebuilding system
      features. Examples include timer/alarm where supported, camera,
      files, calendar, photos, voice recording, opening apps and other
      App Intent/Shortcut/system actions.

1625. QUICK ACTION CAPABILITY AUDIT Before claiming a quick action,
      verify current App Intents/App Shortcuts/Assistant Schemas/system
      framework/deep-link support and test it on a real iPhone.
      Unsupported actions must not be reported as completed.

1626. CAMERA FAST ACTION “Take a photo” should open/execute the shortest
      legitimate camera flow with no AI or unnecessary menus. Save to
      authorized system photo storage as permitted.

1627. CAMERA COMPOUND ACTIONS “Take a photo and send to Oleg”, “take a
      photo and translate”, “take a photo and find this product” are one
      coherent user task: capture → requested action, without
      unsolicited extra processing.

1628. CAMERA LIVE TRANSLATION “Translate this sign/page/paragraph”
      should open camera, recognize text/language locally/system-first
      where possible, allow region selection and show translation
      over/near the original. Do not use paid AI for routine
      OCR/translation when local/system tools suffice.

1629. TRANSLATION TTS ONLY WHEN ASKED “Read the translation” may invoke
      system TTS. Do not automatically narrate or persist translated
      content without user intent.

1630. CAMERA PRODUCT / BARCODE / QR Support barcode/QR/OCR-based exact
      product identification and action flows using legitimate
      local/system mechanisms. Exact SKU/model/variant should drive
      structured shopping search when available.

1631. QR SAFETY Recognize QR payload type locally. Do not auto-execute
      potentially dangerous, financial or irreversible QR actions
      without appropriate confirmation.

1632. VISUAL PRODUCT SEARCH Support photo-based visual product search
      where technically legitimate. Clearly distinguish probable visual
      similarity from exact SKU/barcode identification; never state
      “exact” without evidence.

1633. VEHICLE PLATE / VEHICLE INFO — UKRAINE-SCOPED AND PRIVACY-BOUND
      Where a lawful official/licensed Ukrainian source exists, the
      camera may recognize a license plate and retrieve only legally
      available non-personal vehicle information such as
      make/model/status fields permitted by the source. Do not expose
      owner PII from dubious databases. Visual make/model may be
      compared with returned vehicle data only as a confidence check.

1634. UKRAINE-ONLY EMERGENCY V1 V1 emergency integration is
      Ukraine-scoped: 112/101/102/103/104 and the official 112 Ukraine
      mechanisms where current official integration allows. The goal is
      fastest legitimate connection to a real operator/service, not fake
      automated dispatch.

1635. ENGINEERING JUDGMENT — OUTCOME OVER RIGID METHOD The specification
      defines product outcomes, safety/truth/privacy guardrails and
      evidence expectations. It is not intended to force inefficient
      ceremony or freeze Codex into an inferior implementation method.
      Codex may choose a simpler, faster or more maintainable approach
      when it preserves or improves the required user outcome and
      remains legitimate, testable and maintainable.

1636. HARD GUARDRAILS ARE LIMITED TO REAL RISK Treat safety, legality,
      privacy, security, fraud/deception prevention, secret handling,
      unsupported/private API boundaries, irreversible financial actions
      and destructive data changes as non-negotiable guardrails. Treat
      ordinary architecture/process/UX wording as outcome-oriented
      guidance that may be adapted with evidence when a better
      implementation exists.

1637. CODEX LIMIT-EFFICIENT EXECUTION Codex usage/time is a finite
      engineering resource. Parse/inspect once, cache stable
      conclusions, reuse verified evidence, batch independent checks,
      avoid rereading the whole specification during a task, avoid
      duplicate builds/provider calls, and stop work on a block once
      acceptance evidence is sufficient. When session/usage limits are
      becoming constrained, checkpoint state clearly before consuming
      budget on low-value repetition.

1638. BOUNDED RETRY / PATH-CHANGE JUDGMENT Avoid unchanged deterministic
      retries, but do not apply a mechanical zero-retry rule. A bounded
      verification retry is legitimate for transient failures, flaky
