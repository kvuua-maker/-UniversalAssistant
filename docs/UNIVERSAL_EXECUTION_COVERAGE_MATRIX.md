## Canonical reconciliation: general information

The current `request → native Search is ready card → explicit HTTPS Google handoff` is an **INTERMEDIATE_FALLBACK_ONLY** mechanism, not a native in-app researched answer. It is truthful, minimized, and user-controlled, but the repository contains no production general-retrieval provider, provenance-bearing answer model, or in-app synthesized result renderer. Existing canon requires broad fresh retrieval and approved AI reasoning where needed, while provider/privacy/cost configuration remains absent. Completing a richer answer path without choosing an approved search/AI provider and result/provenance contract would change provider strategy and UX; therefore that increment is `DESIGN_DECISION_REQUIRED` plus external provider configuration, while the existing handoff remains a legitimate supported fallback.

## Sweep conclusions

- The previous generic `.recognized` terminal branch could falsely resemble completion for every parsed-but-unwired capability. It now fails truthfully with `no_production_executor`; this is not a substitute for the missing executor.
- The already-existing recorder controller is now invoked for `.audioRecord` through the production request entry; its physical microphone/file behavior remains a live test.
- Weather, voice, diagnostics, EventKit, MusicKit readiness, and verified Build 21 paths were not rewritten.
- All remaining production-entry gaps above either require a canonical interaction/result contract not present in the repository, an approved/eligible provider, or physical evidence. They are not safe targets for speculative phrase handlers or fake adapters.
